# Testing Guide

## Philosophy — why synthetic ground-truth data

Real vibration is, by definition, invisible to the naked eye — there's no
way to look at real footage and just "know" if the system got the right
answer. So instead of testing against real footage, this project uses
**synthetic test clips with an exact, known correct answer built in**,
generated by `test_clips/generate_test_clips.py`. This lets every claim
about detection accuracy be checked against ground truth, not eyeballed.

## Generating test data

```bash
cd test_clips
python generate_test_clips.py
```

Produces **six** files (three scenarios, each saved two ways):

| File | Ground truth | Should be detected? |
|---|---|---|
| `vibrating_panel.mp4` | Real 15 Hz vibration, 0.3px amplitude | ✅ Yes |
| `static_panel.mp4` | Zero motion | ❌ No |
| `camera_shake.mp4` | Random, non-periodic jitter (2px std) | ❌ No |
| `*_lossless.npy` (one per clip above) | Identical underlying data, saved with **zero compression** | Used to isolate algorithm correctness from video-compression effects |

The `.npy` (lossless) versions exist specifically because testing revealed
standard `.mp4` compression can distort or bury small real signals — see
[`../ml/vibration-analysis.md`](../ml/vibration-analysis.md) for the full
investigation. Testing against both versions lets you tell "is the
algorithm wrong" apart from "is compression the problem."

## Manual verification scripts

These are one-off, disposable scripts (not an automated test suite) used
during development to check specific pieces of logic against known
answers. Run from the `backend/` folder, with the virtual environment
activated.

**Check FFT correctly finds a known frequency:**
```python
import sys
sys.path.insert(0, '.')
import numpy as np
from app.io.video_io import read_video_frames
from app.analytics.vibration import compute_fft_spectrum

frames, fps = read_video_frames('../test_clips/vibrating_panel.mp4')
signal = frames[:, 120, 140, 0]
freqs, magnitude = compute_fft_spectrum(signal, fps)
nonzero = freqs > 0.5
peak_freq = freqs[nonzero][np.argmax(magnitude[nonzero])]
print(f'peak found at: {peak_freq:.2f} Hz  (ground truth: 15.00 Hz)')
```

**Check the full detection pipeline across all three clips:**
```python
import sys
sys.path.insert(0, '.')
from app.io.video_io import read_video_frames
from app.analytics.vibration import analyze_vibration

roi = (135, 40, 10, 160)  # tight box on the bar's left edge
for name in ['vibrating_panel', 'static_panel', 'camera_shake']:
    frames, fps = read_video_frames(f'../test_clips/{name}.mp4')
    result = analyze_vibration(frames, fps, roi=roi, low_hz=10, high_hz=20, peakiness_threshold=10.0)
    print(f"{name:20s}  {result['metrics']}")
```

## Real end-to-end validation results

The results below were produced by running the **actual live API** (not a
standalone script) — upload → roi → process → status → result, through
`curl`, using the synthetic clips above.

| Test clip | Ground truth | Frequency found | Flag returned | Correct? |
|---|---|---|---|---|
| `vibrating_panel.mp4` | Real 15 Hz vibration | 15.063 Hz | `periodic_vibration_detected` | ✅ |
| `static_panel.mp4` | No motion at all | 15.063 Hz\* | `no_vibration_detected` | ✅ |
| `camera_shake.mp4` | Random, non-periodic jitter | 14.31 Hz\* | `no_vibration_detected` | ✅ |

**\*Important finding:** both negative-control clips reported a dominant
frequency *close to or identical to* the real signal's. Frequency alone
would have produced two false positives here — it's the **peakiness
test**, not the frequency reading, that correctly told them apart. This is
the strongest single piece of evidence for why detection is built around
statistical peak-sharpness rather than raw frequency or amplitude.

## Known limitations surfaced through testing

- **Video compression can bury small vibrations** — confirmed by directly
  comparing compressed vs. uncompressed analysis of identical underlying
  data (see `ml/vibration-analysis.md`, Bug 1).
- **ROI selection is functionally necessary** — whole-frame analysis
  dilutes a small, localized vibration into surrounding noise (Bug 2).
- **Amplification has empirically-found safe limits**, different per
  algorithm (baseline: pixel clipping; phase-based: phase-wrapping
  distortion) — not derived from a formula.
- **Larger-amplitude motion may be harder to detect than very small
  motion** on a fixed, narrow ROI — an open question, not fully confirmed
  (see the non-monotonic amplitude-sweep finding in `ml/vibration-analysis.md`).
- **FFT frequency resolution is tied to clip length** — approximately
  0.25 Hz per bin at 4 seconds / 60fps. Longer clips give finer resolution
  at the cost of needing more footage before producing a result.
- **The detection threshold (`peakiness_threshold`) was calibrated against
  a small number of synthetic test clips** — a real, evidence-based choice,
  but not yet validated against a large variety of real-world footage.

## What's not yet covered

- No automated test suite (e.g. `pytest`) exists yet — all testing so far
  has been manual, using the scripts above and the live API. This would be
  a natural next step for `backend/tests/`.
- No tests exist yet for the API layer itself in isolation (e.g. malformed
  requests, concurrent job handling, edge cases in ROI bounds).
